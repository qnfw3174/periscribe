🔐 Periscribe — CA(인증서) 동작

프록시가 Claude↔Anthropic TLS 를 복호화하려면 자체 CA 가 필요하다. 누가 만들고, 누가 신뢰시키고, 언제 적용되는지.

1. 무엇을 만드나 (생성: 프록시 서버 담당)

periscribe-proxy.exe 가 처음 실행될 때 proxycert.ensure_certs() 로 2개 인증서를 만든다. 누락/만료(리프 잔여 30일 미만) 시에만 재발급한다. 관리자 불필요 — Windows 인증서 저장소가 아니라 파일로만 둔다.

인증서주체(CN)키/서명유효기간용도
ca.pem (+ ca.key)Periscribe Local CARSA-2048 · SHA-256
BasicConstraints ca=true, pathlen=0		3650일리프를 서명하는 루트. Claude 가 신뢰할 대상
server.pem (+ key)127.0.0.1CA 가 서명 · EKU=serverAuth
SAN: 127.0.0.1 / ::1 / localhost		825일프록시가 TLS 핸드셰이크에서 제시하는 서버 인증서
🔒 이 CA 의 권한은 localhost 한정. 리프 SAN 이 127.0.0.1/::1/localhost 뿐이라, 이 CA 로는 그 외 도메인을 위장할 수 없다(브라우저·외부 사이트 MITM 불가). 개인키(ca.key)는 그 PC 로컬에만 있다.

2. 어떻게 신뢰시키나 (신뢰: 컬렉터 = 머신 담당)

Claude Code 는 Node 로 동작하고, Node 는 환경변수 NODE_EXTRA_CA_CERTS 가 가리키는 CA 를 기본 신뢰 묶음에 더해 신뢰한다. 컬렉터(periscribe.exe)는 프록시가 만든 ca.pem의 경로 문자열만 ~/.claude/settings.json 의 env 에 써넣는다. → 컬렉터는 cryptography 를 쓰지 않고 CA 를 만들지도 않는다(역할 분리).

언제 CA 가 settings 에 들어가나
  • 프록시 켜기 — route_to_proxy() 가 ANTHROPIC_BASE_URL(라우팅)과 NODE_EXTRA_CA_CERTS(신뢰)를 함께 기록.
  • 패널 첫 실행 — _ensure_ca_resident() 가 CA 만 미리 기록(라우팅은 직결 유지 = 프록시 OFF). → 무중단 ON 준비.
왜 따로 쓰나

CA 와 라우팅은 적용 타이밍이 다르다(§3). CA 를 미리 상주시켜 두면, 나중에 라우팅만 켜도 떠 있는 세션이 안 끊긴다.

3. ⏱ 핵심: 적용 타이밍이 다르다 (왜 "처음 1회 재시작"이 생기나)

env 키Claude 가 읽는 시점실행 중 세션에…
ANTHROPIC_BASE_URL (라우팅)매 API 호출마다 핫리로드즉시 반영 — 켜기/끄기가 바로 적용
NODE_EXTRA_CA_CERTS (CA 신뢰)프로세스 시작 시 1회만소급 적용 불가 — CA 없이 시작된 세션은 재시작해야 신뢰
그래서 CA 가 없던 상태에서 처음 켜면, 그때 떠 있던 세션은 우리 CA 를 모른 채 시작됐으므로 프록시 경유 시 TLS 실패 → 그 세션만 1회 재시작 필요.
해결: 컬렉터 패널을 한 번 열면 CA 가 미리 상주(_ensure_ca_resident)한다. 그 이후 시작된 모든 세션은 CA 를 이미 신뢰하므로, 라우팅을 켜고/꺼도 무중단.

4. CA 상주 규칙 (OFF 에도 유지, uninstall 에만 제거)

  • 프록시 끄기(strip_proxy_env()): ANTHROPIC_BASE_URL 만 직결값으로 덮어쓴다. CA 는 그대로 남긴다. — 다음 켜기를 무중단으로 만들기 위해.
  • OFF 인데 CA 가 남아도 무해: 라우팅이 직결이라 트래픽은 진짜 api.anthropic.com 으로 정상 TLS. CA 는 신뢰 목록에만 있고 쓰이지 않는다(localhost 한정이라 영향 없음).
  • 완전 제거(strip_proxy_env(include_ca=True)): periscribe.exe uninstall 일 때만 NODE_EXTRA_CA_CERTS 키까지 제거.
  • env 의 키는 삭제가 아니라 값 덮어쓰기로 다룬다 — Claude 는 settings env 를 프로세스 env 에 병합만 해서, 키 삭제는 실행 중 세션에 반영되지 않기 때문(lockout 방지).

5. TLS 가로채기 흐름

  • ⑥ Claude → https://127.0.0.1:8077(프록시). 프록시가 리프(server.pem)를 제시 → Claude 가 우리 CA(신뢰됨)로 검증 통과 → 핸드셰이크 성립.
  • 프록시가 평문으로 복호 → 정책 검사(차단/레닥션/주입 + 응답 tool_use 게이팅) + 로깅.
  • ⑦ 프록시 → api.anthropic.com 으로 공개 CA 정상 TLS 재암호화 중계. 응답도 같은 경로로 역중계.
  • 컬렉터의 헬스체크도 같은 ca.pem으로 프록시와 TLS 핸드셰이크를 시도해 "서버 가동 중"을 검증한다(가동 확인 후에만 라우팅 ON).

6. 중앙 서버 모드(향후)와의 관계

프록시 서버를 중앙 서버 1대로 옮기면, 신뢰시킬 CA 가 그 서버의 CA로 바뀔 뿐 메커니즘은 동일하다: 각 머신 컬렉터가 NODE_EXTRA_CA_CERTS=서버 CA, ANTHROPIC_BASE_URL=서버 주소로 라우팅. 리프 SAN 만 서버 호스트명/IP 로 확장하면 된다(설계: docs/central-proxy-design.md).
